# Matrice source-de-vérité du chiffrage — 3D Reader

> **Périmètre :** module de chiffrage `web/chiffrage/*` (`model.js`, `routes.js`, `tooling.js`, `cores.js`, `rfq.js`, `store.js`, `ui.js`, `workbook.js`), page Analyse 3D (`web/app.js`, `web/engine/*`) et volet IA (`web/ai-workspace.js`, `web/engine/ai-context.js`, `semantic.js`, `foundry-knowledge.js`, `api/ai.js`), branche `claude/3d-reader-uxw782`.
> **Méthode :** une cartographie par domaine, établie depuis le code puis contre-vérifiée. Les corrections issues de la vérification sont intégrées.
> **Confidentialité :** aucune valeur calée de l'entreprise n'apparaît (taux, €/kg, coefficients de cycle, TRS, marges…). Le document nomme les paramètres sans citer leur valeur. « Défaut du code » désigne une valeur neutre codée en dur, qui n'est pas reproduite ici.

---

## 1. Objet et hiérarchie des sources

Pour chaque sortie du chiffrage, ce document indique :
- d'où vient sa valeur aujourd'hui et dans quel ordre de priorité ;
- la règle qui la calcule et le repli quand une donnée manque ;
- la confiance qu'on peut lui accorder ;
- ce que l'IA a le droit d'en faire et ce qu'une personne doit valider.

Il compare ensuite le comportement du code à la hiérarchie voulue.

| Niveau | Source | Autorité | Repère utilisé dans la matrice |
|---|---|---|---|
| 1 | Commande client ou donnée imposée : RFQ « commande série » importée (`rfq.js`), valeurs saisies dans le devis | **hard** | `[N1-RFQ]`, `[N1-saisie]` |
| 2 | Règles actuelles de l'entreprise : onglet Paramètres (`settings`), classeur de chiffrage `.xlsm` importé, fichier d'indices métal | **hard** | `[N2-param]`, `[N2-classeur]`, `[N2-indices]` |
| 3 | Géométrie 3D mesurée ou déterminée : volume, masse, bbox, épaisseurs, module, corps, features sémantiques | **evidence** | `[N3-3D]` |
| 4 | JSON des tendances historiques (fichier de paramètres calés) | **soft_prior** | `[N4]` |
| 5 | LLM (Qwen local via Ollama, ou passerelle OpenAI) | **reasoning_only** | `[N5-IA]` |
| — | Valeur par défaut codée en dur (hors hiérarchie) | default_code | `[D-code]` |

**Principes**
- Une tendance historique (N4) n'écrase jamais un paramètre explicite actuel (N1 ou N2).
- Le LLM (N5) n'invente ni prix, ni temps de cycle, ni nombre de noyaux sans preuve, ni règle métier. Il explique, compare et signale.
- Chaque valeur doit être traçable : valeur, source, autorité, confiance, écart, hypothèses, validation humaine.
- Une valeur par défaut du code n'est pas une règle de l'entreprise : elle doit apparaître comme une hypothèse.

**Constat central, confirmé dans le code.** Le JSON calé s'importe par Paramètres → « Importer des paramètres ». La chaîne est `ui.js:importFile` (branche `settings`) → `store.js:mergeSettings` → `store.js:saveSettings` → `loadSettings`, et elle écrit sous la **même clé de stockage** que les saisies de Paramètres. Ce JSON agit donc aujourd'hui comme un **paramètre hard de niveau 2** :
- la dernière écriture gagne ;
- aucune provenance n'est conservée ;
- aucun écart à la tendance ne peut être calculé.

**Notations utilisées dans la matrice**
- `[N2-param ≡ N4]` : même emplacement `settings.*`, rempli indifféremment par une saisie Paramètres ou par le JSON calé. Le dernier écrit gagne.
- **Îlot imposé** : procédé choisi à la main (`p.procede ≠ auto`), qui existe dans `settings.processes` et dans le classeur.
- **0 silencieux** : repli à zéro sans aucune alerte.

## 3. Écarts entre le code actuel et la hiérarchie voulue

1. **Le JSON de tendances agit comme un paramètre hard (N4 traité comme N2).**
   - **Constat.** `ui.js:importFile` (branche `settings`) → `store.js:mergeSettings` → `store.js:saveSettings` → `loadSettings`, sous la même clé de stockage que les saisies de Paramètres. Conséquences :
     - le dernier écrit gagne : un import écrase une saisie faite avant dans Paramètres, et une saisie faite après écrase la tendance ;
     - rien n'est conservé de l'origine (ni nom, ni date, ni version), alors que le classeur, les indices et la RFQ gardent leur nom et leur date d'import ;
     - les tableaux (`bandes`, `coefPoids`, `types`, `finitions`) sont remplacés en bloc, sans complétion de leurs éléments ;
     - les objets partiels sont complétés sans le dire par les défauts du code ;
     - aucun schéma n'est vérifié : une clé de premier niveau non lue est ignorée, mais une nouvelle clé dans un dictionnaire devient active (nouvel îlot dans `processes`, nouvelle opération, nouveau niveau de complexité, nouvel alliage dans `densities`) ;
     - « Exporter les paramètres » ressort le mélange tendance + saisies ;
     - « Paramètres par défaut » demande une confirmation qui ne dit pas que les valeurs calées seront perdues ;
     - l'onglet Paramètres présente lui-même le fichier calé comme « valeurs de départ » à importer.

     Clés concernées : `processes.*` (cycle, miseAuMille, rendement, capacités, qualite, outillage, finitions, tth, noyaux), `operations.*`, `trs.*`, `tooling.*`, `cores.*`, et toute clé `marge`, `tauxMini`, `energy`, `modes`, `inflation` ou `densities` si le fichier en contient.

     Vérifié sur le vrai fichier : ses clés sont bien celles du code (`processes.*.cycle.exposant`, `rendement.base`, codes d'opérations, `tooling`, `cores`). Les noms anglais vus dans la synthèse de conversation ne sont qu'une traduction de présentation : les valeurs sont donc bien lues et appliquées.
   - **Proposition.**
     - Stocker le JSON dans une couche `prior` séparée, sous sa propre clé de stockage : `{fichier, importéLe, version, valeurs}`.
     - Valider l'import contre un schéma, avec un rapport des clés inconnues ou mal nommées ; refuser un îlot ou une opération incomplets.
     - Résoudre chaque valeur dans cet ordre : `explicite (N1/N2) ?? prior (N4) ?? défaut du code`.
     - Calculer `ecart_tendance` dès qu'une valeur explicite et une valeur prior existent toutes les deux.
     - Afficher la tendance et l'écart à côté de chaque champ de Paramètres. Ajouter un bouton « Adopter la tendance » (par valeur ou par bloc) qui écrit dans Paramètres avec provenance, date et validation humaine.
   - **Mis en œuvre (couches de paramètres).** `store.js` garde les tendances sous leur propre clé (`reader3d.chiffrage.tendances.v1` : nom du fichier, date d'import, valeurs). L'import « Importer des tendances (fichier de paramètres calés) » est validé (`validateTendances`) : clés inconnues ou mal orthographiées signalées avec une suggestion puis ignorées, valeurs hors bornes refusées, lignes de tableau incomplètes complétées et signalées, traitement thermique nouveau sans coefficient refusé. Les îlots et opérations restent une liste fermée : un code inconnu est ignoré. Ordre de résolution, valeur par valeur : `saisie ?? classeur ?? tendance ?? défaut du code`. Le classeur (N2) passe avant la tendance (N4), conformément à la hiérarchie. Paramètres affiche l'origine de chaque nombre, la tendance et l'écart relatif quand une valeur actuelle s'en écarte, et le bouton « Adopter la tendance ». Deux exports séparés : saisies et tendances. Deux effacements, chacun précisant ce qui est conservé.

2. **Les défauts du code et du classeur sont figés comme s'ils étaient des saisies explicites.**
   - **Constat.**
     - `saveSettings(settings)` enregistre l'objet complet dès la première modification dans Paramètres (`ui.js:onChange`) ou dès le premier import JSON. Ensuite, `loadSettings` fait `{...défauts, ...sauvegardé}`. Les défauts du code et les valeurs du classeur (marge B135, taux mini AA156, inflation, coefficient de sécurité, heures de changement) deviennent « sauvegardés ». Ils priment alors sur un classeur réimporté et ne se distinguent plus d'une saisie.
     - Même mécanisme côté devis : `store.js:defaultQuote` copie les valeurs du classeur à la création (prix d'achat, PAF, premium, `vaUsinage`, `rebutUsinage`, `tailleSerie`, `coefDifficulte`) et `importFile` ne les rafraîchit jamais (`{...defaultQuote, ...q}`).
     - `premiereAnnee`, `volumeAnnuel` et `annees` du code sont conservés comme `USER_FIELDS` au premier import et passent avant Liste!A2.
   - **Proposition.**
     - N'enregistrer que les clés réellement modifiées, chacune avec `{valeur, source: 'saisie', date}`.
     - Recalculer la valeur effective à chaque chargement à partir des couches : classeur courant, prior, code.
     - Dans le devis, séparer une valeur « héritée du classeur » (recalculée) d'une valeur « saisie » (figée).
   - **Mis en œuvre pour Paramètres (couches de paramètres).** Seules les clés saisies sont enregistrées (`reader3d.chiffrage.settings.v2`, `{valeur, source: 'saisie', date}` par chemin), et la valeur effective est recalculée à chaque chargement (`loadSettingsLayers`). L'objet complet des versions précédentes est migré une fois : ses valeurs deviennent des saisies, sauf celles égales au défaut du code ou du classeur au même endroit, et les valeurs vides. Il reste stocké tel quel, comme sauvegarde, jusqu'à « Effacer mes saisies ». Le devis (`defaultQuote`, `USER_FIELDS`) n'est pas encore traité (étape 7).

3. **Un champ vidé vaut 0, au lieu de laisser la main à la source suivante.**
   - **Constat.** `ui.js:readValue` renvoie null pour un champ vide ; ce null écrase le défaut dans `loadSettings`, puis les formules le traitent comme 0. Effets observés :
     - marge, coefficient de sécurité, heures de changement et inflation à 0 ;
     - rendement type à 0, donc mise au mille maximale ;
     - mise au mille par défaut null, donc `kgCast` = 0 ;
     - forfait d'outillage à 0, tiroirs à 0, taux mini cible à 0 ;
     - `chargeKg` null, donc 1 pièce par charge et coût maximal ;
     - PAF, prix d'achat et premium vidés : 0 ;
     - TRS vidé : retour au défaut du code, alors que l'écran affiche un autre repli.
   - **Proposition.** Un champ vide signifie « non renseigné » : la valeur passe à la couche suivante et une alerte s'affiche. Un 0 n'est accepté que s'il est saisi explicitement, et il est refusé là où il n'a pas de sens (TRS, densité, `chargeKg`, mise au mille).
   - **Mis en œuvre pour Paramètres (couches de paramètres).** Un champ vidé retire la saisie, et la couche suivante reprend la main. Un 0 tapé est conservé. Il est refusé, avec un message, pour le TRS (borné à ]0 ; 100 %]), la densité, `chargeKg` et la mise au mille par défaut. Aucune valeur vide n'atteint plus les formules. Le TRS affiché dans le devis est celui de la gamme. Restent à traiter : les champs du devis (PAF, prix d'achat, premium) et l'alerte prévue à l'étape 8.

4. **Des données de commande (N1) existent dans la RFQ mais ne sont pas lues.**
   - **Constat.** `rfq.js:readSeriesOrder` et `rfq.js:metalOf` ignorent :
     - « Poids Brut vendu (en kg) » et les dimensions L×l×h (1- Données GO NO GO, 3- Données de chiffrages) ;
     - « Mise au mille », « Poids vendu (kg / pc) » et « Taux de rebuts usinage » (5- Chiffrage Fonderie) ;
     - « % de rebut d'usinage » (6- Chiffrage Usinage), « Casting weight » (7- Synthèse Commerce), « Poids du brut de fonderie » (8- Analyse du projet), « Taux de rebut » (Pré-étude Moule SP) ;
     - tout l'onglet « 4- Outillage » : noyaux BAN, première dotation, renouvellement, durée de vie par empreinte, essais noyaux, taux ;
     - empreintes, conditionnement, productivité, opérations autres que le TTH dans le champ « Autres ».

     « Fonderie » sert seulement à une alerte ; le champ Usinage est seulement affiché.
   - **Proposition.**
     - Étendre la lecture : les dispositions libellé / valeur (A/B, C/D) sont déjà gérées.
     - Stocker ces valeurs dans `q.serie` comme données N1.
     - Les appliquer en priorité (poids, mise au mille, taux de rebut) ou, au minimum, calculer l'écart avec l'estimation (poids 3D / poids brut vendu, bbox / L×l×h).
     - Faire de « Fonderie » un îlot imposé par défaut, avec dérogation tracée.
   - **Mis en œuvre (données RFQ), en partie.** `rfq.js:readSeriesOrder` lit aussi « Poids Brut vendu (en kg) » (1- Données GO NO GO, libellé en A, valeur en B), « Poids vendu (kg / pc) », « Mise au mille » et « Taux de rebuts usinage » (5- Chiffrage Fonderie, libellé en C, valeur en D) et les range dans `q.serie` (`poidsBrut`, `poidsVendu`, `miseAuMille`, `rebutUsinage` ; une mise au mille ≥ 100 est lue pour 1 000 kg, un taux > 1 en pourcentage). Ces valeurs ne sont **pas appliquées** : les appliquer automatiquement est une décision laissée à l'utilisateur. Elles sont ajoutées aux traces comme autres sources (`rfq`, hard) : `piece.poids` et `piece.miseAuMille` quand une seule pièce est chiffrée, `ensemble.poids` et `ensemble.miseAuMille` (kg coulés / poids de l'ensemble) pour un ensemble, `devis.rebutUsinage`. Un écart au-delà de la tolérance (10 % pour chacune, `provenance.js:DEMANDE`) donne l'alerte « écart à la demande client », à valider, propagée jusqu'au prix. La carte « Commande série » les compare au chiffrage (demande, chiffrage, écart) et l'export les reprend dans l'onglet « Commande série ». Restent non lus : dimensions L×l×h, onglets 4, 6, 7, 8 et Pré-étude Moule SP, empreintes, conditionnement, productivité.

5. **Saisie et RFQ se partagent les mêmes champs : la dernière écriture gagne.**
   - **Constat.**
     - `ui.js:applySeriesOrder` écrit dans les champs de saisie : alliage, mois, cours, typologie, prix d'achat et de vente, PAF, MOQ, `tailleSerie`, `prixCible`.

     - « Retirer » la RFQ conserve les valeurs qu'elle avait écrites.
     - Pour le TTH, c'est l'inverse : la saisie prime sur la RFQ.
     - L'aide « selon la demande client » s'affiche dès que TTH = Aucun, ce qui peut induire en erreur.
   - **Proposition.** Conserver séparément la valeur RFQ (`q.serie`) et la surcharge saisie. Valeur effective = `surcharge ?? RFQ ?? N2`. Afficher la provenance et l'écart. Appliquer la même règle à tous les champs.

À l'import, les valeurs remplacées sont gardées (`q.serieAvant`, celles d'avant la première RFQ). « Retirer » liste les champs qui gardent encore une valeur écrite par la RFQ (et qui n'avaient pas déjà cette valeur) ; la carte « Commande série » propose « Remettre les valeurs d'avant l'import » ou « Garder ces valeurs » (`q.serieRetiree`). La bascule « Prototype » ne remplace que des volumes venus de la RFQ (volumes série ou proto de la demande, `rfq.js:programmeFor`) ; des volumes saisis sont conservés, avec un message. L'aide « selon la demande client » du TTH ne s'affiche que si le TTH de la pièce n'est pas choisi. Restent : la séparation surcharge / RFQ pour chaque champ (`q.overrides`, étape 7).

7. **Le prix d'achat du métal n'est pas indexé.**

Les réponses locales sont en texte simple depuis la suppression d'`ANSWER_SCHEMA` ; la passerelle répond avec `analyse_chiffrage` au lieu de `quote`. ## 5. Proposition de mise en œuvre

### Étape 1 : transformer la matrice en registre exécutable
Créer `web/chiffrage/provenance.js`. Pour chaque sortie, il décrit les sources candidates dans l'ordre de priorité, la règle de confiance et la règle de validation humaine. Ce registre sert à la fois de spécification et de base aux tests de couverture.

### Étape 2 : séparer les couches de paramètres (correction de l'écart n° 1)
- Couches distinctes :
  - `settings` : uniquement les saisies de Paramètres, avec la provenance de chaque clé ;
  - `prior` : le JSON calé, avec fichier, date d'import et version ;
  - `classeur` : déjà séparé ;
  - `code` : les défauts.
- `loadSettings` renvoie `{effectif, provenance}`.
- L'import JSON écrit seulement dans `prior`. Il est validé contre un schéma et produit un rapport des clés inconnues, mal nommées ou incomplètes.
- Paramètres affiche pour chaque champ la valeur effective, sa source, la tendance et l'écart, et propose le bouton « Adopter la tendance », tracé et soumis à validation.
- « Paramètres par défaut » précise ce qui sera effacé.

### Étape 3 : donner un sens à « vide » et à « 0» (écarts n° 3 et 8)
- Un champ vide passe la main à la couche suivante, avec une alerte.
- Un 0 n'est accepté que s'il est explicite et qu'il a un sens.
- Tout repli à 0 produit une valeur de confiance nulle.

### Étape 4 : objet « valeur tracée » et résolution
```js
/**
 * @typedef {Object} ValeurTracee
 * @property {number|string|boolean|null} valeur
 * @property {string} unite
 * @property {{type: 'saisie'|'rfq'|'parametres'|'classeur'|'indices'|'geometrie'|'tendance'|'calcul'|'defaut_code',
 *             ref: string,                 // "store.js:settings.trs.ASN", "rfq.js:metalOf", "app.js:partFeatures"…
 *             fichier?: string, date?: string,
 *             entrees?: string[]}} source  // pour une valeur calculée : clés des valeurs d'entrée
 * @property {'hard'|'evidence'|'soft_prior'|'default_code'|'reasoning_only'} autorite
 * @property {1|2|3|4|5|null} niveau
 * @property {{niveau: 'haute'|'moyenne'|'faible'|'nulle', raison: string}} confiance
 * @property {{tendance: number, ecart_abs: number, ecart_rel: number, seuil: number|null, alerte: boolean}|null} ecart_tendance
 * @property {Array<{source: string, valeur: any}>} alternatives  // sources disponibles non retenues (RFQ / 3D / indice…)
 * @property {string[]} hypotheses
 * @property {{requise: boolean, statut: 'a_faire'|'validee'|'refusee', par?: string, date?: string, motif?: string}} validation_humaine
 */
```
- `resoudre(cle, candidats)` :
  - retient le premier candidat non vide dans l'ordre du registre ;
  - consigne les autres dans `alternatives` et calcule leurs écarts ;
  - vérifie qu'un candidat `soft_prior` n'est jamais retenu quand un candidat `hard` existe ;
  - n'accepte jamais de candidat `reasoning_only`.
- Une valeur dérivée (kgCast, coût d'un centre, prix) a `source.type = 'calcul'` et la liste de ses entrées. Sa confiance est la plus faible de celles des entrées. Une validation lui est requise si l'une des entrées en requiert une.
- **Mis en œuvre (`provenance.js`).** `traced`, `resolve`, `derive`, `fromSetting` (provenance tirée des couches de `store.js`) et `settingsGroup` (paramètres d'une estimation, regroupés). Les candidats sont passés dans l'ordre du registre : le premier non vide est celui que le calcul a utilisé. Une tendance n'est jamais retenue devant une valeur `hard`, une réponse de l'IA jamais. Écarts : `ecart_tendance` (seuil réglable dans Paramètres, 15 % par défaut) et alerte « sources divergentes » entre sources actuelles. La validation humaine n'est pas encore stockée (`validation_requise` est un booléen) : voir l'étape 8.

### Tests (`tests/js/`)
1. **Hiérarchie.** Saisir un TRS dans Paramètres, puis importer un JSON qui en contient un autre : la valeur effective reste la saisie et `ecart_tendance` est calculé. Faire l'inverse (import, puis saisie) donne le même résultat.
2. **Prior sans valeur explicite.** Le prior est retenu avec `autorite: soft_prior` et une validation requise ; sans prior, c'est le défaut du code, avec une alerte.
3. **Schéma.** Une clé inconnue ou mal nommée apparaît dans le rapport ; un îlot incomplet est refusé ; un tableau partiel ne produit plus de NaN.
4. **Vide et zéro.** Un champ vidé passe à la couche suivante avec une alerte, et ne vaut jamais 0 (marge, coefficient de sécurité, `chargeKg`, rendement, mise au mille par défaut).
5. **RFQ et saisie.** La valeur RFQ est conservée après une surcharge ; retirer la surcharge ramène la valeur RFQ ; la bascule « Prototype » n'écrase pas les volumes saisis.
6. **Propagation.** Une mise au mille ou des empreintes imposées recalculent les kg coulés par cycle, le cycle et le moule ; le classement tient compte des saisies.
7. **Replis.** Un cours de vente manquant donne une confiance nulle, une alerte et un export marqué ; un îlot imposé infaisable exige une dérogation.
8. **Couverture.** Chaque sortie du registre a une trace complète dans `compute()` sur la fixture.
9. **Valeurs dérivées.** La confiance d'un prix vaut la plus faible de ses entrées ; un statut de validation est invalidé quand une entrée change.
10. **Export.** L'onglet « Traçabilité » est présent et ses colonnes sont complètes ; les fichiers et leurs dates figurent dans l'en-tête.
11. **IA.** Le contexte contient `costing_trace` mais ni `quote` ni `costing_contract`. Un espion sur `store` vérifie qu'aucune écriture ne part de l'IA. Une réponse contenant un prix ou un taux inventé est marquée « non vérifiée ». Le contexte envoyé à la passerelle masque les montants internes.
12. **Non-régression.** Sur la fixture synthétique, les prix restent identiques tant qu'aucune couche ne change. Une comparaison aux résultats d'Excel sur le vrai classeur se fait avec un jeu de données privé, hors du dépôt, pour respecter la confidentialité.
